# 共学回放式 Coding Harness 设计

## 1. 背景与定位

当前仓库已经交付可离线验收的最小 Harness：程序员可以接入 Git 项目、输入需求、批准计划，让自研 Agent 在独立 worktree 中修改代码，并通过确定性反馈闭环完成修正、验证和最终审查。现有实现还包括事件存储、治理护栏、REST/SSE、最小 WebUI、Mock 三机制演示、一键测试、双 CI 和 Docker 静态交付契约。

下一阶段不重写这些能力，而是在其上构建一个具有明确产品特色的“共学回放式 Coding Harness”。它首先帮助程序员理解真实项目中的工程决策：为什么读取或修改某个文件、为什么选择某种实现、验证失败后为什么改变方向，以及最终交付为何可信。同时，Harness 只把用户明确批准的纠正保存为项目经验，使后续任务能够以可追溯方式复用这些经验。

产品核心表述为：

> 让程序员与 Coding Agent 在可验证、可回放、可纠正的工程轨迹中一起学习。

## 2. 本轮范围

本轮采用“共学纵向闭环优先”，只设计和实施以下四个阶段：

1. 真实 DeepSeek/Qwen Provider、凭据生命周期与任务级联网授权。
2. 结构化意图卡、语义检查点、只读提问和引导/自动双执行模式。
3. 不可篡改原轨迹、从检查点创建纠正分支、代码状态恢复和轨迹比较。
4. 项目学习卡候选、用户批准、作用域、版本、检索、冲突处理和引用追踪。

本轮明确不包含：

- 依赖安装、通用工具网络、Git push/merge/release 和外部 checkout filter 的开放。
- 多 Workspace 并发和多 Agent 编排。
- 回放界面的最终视觉设计、高级动画、主题和复杂筛选。
- 公网多用户部署、团队权限和多租户安全边界。

这些能力保留在后续独立规格中，不能借本轮接口提前绕过现有治理策略。

## 3. 已批准的产品决策

1. 产品第一特色是“证据驱动”，最终差异化形态是“共学回放”。
2. 原始轨迹不可改写；用户纠正从选定检查点创建新轨迹。
3. 回放基本单位是结构化意图卡，不展示模型原始思维链、隐藏提示词、凭据或隐私。
4. 回放输入严格区分提问、纠正和补充需求。
5. 用户纠正只生成项目学习卡候选；每次必须询问是否记住。
6. 项目学习卡带作用域、来源、版本和使用记录，而不是普通聊天摘要。
7. 产品提供引导执行和自动执行两种模式，默认使用引导执行。
8. 产品首先帮助用户理解真实项目的工程决策，不定位为编程语法教程或 Agent 调试器。
9. UI 最终设计放到四阶段核心机制完成后；前期沿用当前功能优先的最小界面。

## 4. 增量架构

### 4.1 保留的现有边界

- `LLMProvider` 继续隔离 Mock、DeepSeek 和 Qwen。
- `AgentOrchestrator` 继续负责计划、动作、工具、反馈、预算和停止逻辑。
- `EventStore` 继续保存执行事实，并作为状态恢复和投影的唯一事实源。
- `PolicyEngine`、`ApprovalManager`、`PathGuard`、worktree 和工具注册表继续负责安全执行。
- REST 处理命令，SSE 推送事件，当前 WebUI 继续提供最小操作入口。

不得建立第二套 Agent 主循环，也不得把循环、治理、回放或记忆决策委托给高层 Agent 框架。

### 4.2 新增组件

#### ProviderRegistry 与 CredentialVault

`ProviderRegistry` 管理 Provider 类型、API 地址、模型和启用状态，并依据凭据引用构造现有 `LLMProvider`。`CredentialVault` 只负责保存、更新、读取和删除秘密。本机持久凭据必须使用 OS Keyring；Keyring 不可用时，只能由用户明确选择进程内会话凭据，进程退出即失效，禁止回退到明文文件。容器使用主密码派生密钥和认证加密文件。配置、API、事件和日志只保存凭据引用及状态，不保存明文。

#### IntentProjector

`IntentProjector` 根据已落盘的任务事件、工具结果、验证结果和学习卡引用生成意图卡。意图卡是事实的投影，不是新的执行事实源；重新投影必须得到相同的结构化结果。

#### ReplayService 与 CheckpointStore

`ReplayService` 管理轨迹父子关系、检查点资格、回放查询和纠正分支。`CheckpointStore` 在宿主私有 `state_root` 中保存内容寻址的任务变化清单、摘要和加密变化数据。检查点数据不属于长期记忆，不进入普通 LLM 上下文。

#### InteractionService

`InteractionService` 提供三种互斥命令：

- `QUESTION`：只读解释，不注册工具，不修改任务代码。
- `CORRECTION`：从检查点创建新轨迹和新 worktree。
- `REQUIREMENT_UPDATE`：生成新计划版本，使旧计划批准失效。

#### LearningService

`LearningService` 生成学习卡候选、执行敏感过滤、处理用户批准、管理版本和作用域、检索当前任务所需规则，并记录每次引用。未批准候选永远不能进入 Agent 上下文。

## 5. 核心数据模型

| 模型 | 关键字段与约束 |
|---|---|
| `ProviderProfile` | Provider 类型、HTTPS API 地址、模型、凭据引用、状态；不含明文秘密 |
| `LearningTrace` | Workspace、任务、父轨迹、起始检查点、执行模式、创建时间 |
| `IntentCard` | 目标、事实事件引用、学习卡版本引用、动作、预期结果、实际证据引用、状态 |
| `SemanticCheckpoint` | 轨迹、事件序号、Git 基线、文件清单摘要、加密变化数据引用 |
| `UserInteraction` | 类型、轨迹、检查点、用户输入、结果轨迹或计划版本 |
| `LearningCardCandidate` | 候选规则、建议作用域、来源纠正、敏感过滤结果、状态 |
| `ProjectLearningCard` | Workspace、规则、作用域、正反示例、来源、版本、启用状态、用户优先级 |
| `LearningCardUsage` | 任务、意图卡、学习卡及其版本、实际影响摘要 |

所有新增记录使用稳定 ID、版本或事件序号建立引用。历史轨迹始终引用当时使用的学习卡版本；编辑或删除当前学习卡不能改写历史。

## 6. 用户与系统数据流

### 6.1 创建和运行任务

1. 用户选择 Workspace、DeepSeek/Qwen、模型和执行模式。
2. Harness 校验 Provider 配置与凭据状态，并创建任务级 LLM 网络授权。
3. Agent 生成计划；默认等待用户批准。
4. 每次动作前，Provider 返回严格的 `DecisionEnvelope`：当前目标、事实引用、学习卡引用、拟执行动作、预期结果和验证方式。
5. Harness 校验、限长和脱敏后保存相关事件，并由 `IntentProjector` 生成待执行意图卡。
6. 现有治理和工具链执行动作；真实工具结果、diff 和验证证据回填为意图卡的结果引用。Provider 不能自行声明工具成功。

### 6.2 引导执行

引导模式在计划批准、首次代码修改、验证失败、修复方向变化、危险动作审批和最终交付前形成语义检查点并暂停。自动模式不在普通检查点暂停，但安全审批、预算和最终审查保持不变。

### 6.3 提问

提问只读取选定意图卡、其事实引用和有限相邻上下文。解释请求使用独立只读 Provider 入口，不注册工具。回答作为追加事件保存；它不能改变任务状态、计划、代码、审批或学习卡。

### 6.4 纠正和分支

1. 用户选择可分支检查点并提交纠正。
2. Harness 保存父轨迹、检查点和纠正文本，冻结其引用关系但不修改父轨迹。
3. 新 worktree 从原始 Git 基线创建。
4. Harness 依次复验摘要并重放检查点之前已确认的变化。
5. 创建子轨迹，只继承检查点之前的已确认事实、计划版本、代码状态和当时有效的学习卡引用。
6. 纠正进入新计划或下一次决策；父轨迹仍可继续查看和比较。

### 6.5 项目学习

纠正完成并获得客观验证后，Harness 可以提出学习卡候选。用户可以编辑、批准或拒绝；只有批准版本才可被后续任务检索。后续意图卡必须展示采用了哪张学习卡、哪个版本，以及该规则如何影响当前动作。

## 7. 学习卡检索

首版使用确定性检索，不引入向量数据库：

1. 只读取当前 Workspace 的启用卡片。
2. 按项目、目录、文件类型、语言和工具作用域过滤。
3. 按作用域精确度、用户固定优先级和版本时间排序。
4. 限制卡片数量和总字节数，选择结果可离线复现。
5. 若两条适用规则互相冲突，任务进入 `WAITING_USER`，由用户选择、修改或停用规则。

向量检索只有在确定性版本经过验收后才能另行设计；它不能改变“用户批准后才记忆”和“引用可追溯”两个约束。

## 8. 安全、错误处理与恢复

### 8.1 Provider 与秘密

- 只允许登记的 DeepSeek/Qwen HTTPS 地址，不跟随重定向。
- 真实 LLM 网络授权只适用于当前任务所需 Provider，不扩展到 Shell、安装或其他工具网络。
- 超时、限流和临时服务错误只在尚未发生副作用时有限重试。
- 请求、异常、事件、意图卡和学习卡统一经过现有脱敏边界。
- Provider 状态接口不得通过长度、错误正文或异常细节回显秘密。

### 8.2 检查点与轨迹

- 检查点重放前验证 Workspace 身份、Git 基线、文件摘要和变化数据摘要。
- 任一不一致进入 `WAITING_USER`，不得自动猜测或覆盖用户修改。
- worktree 创建或变化重放中断时保留不确定现场，禁止自动递归清理。
- 检查点变化数据使用独立于 LLM API Key 的安装数据密钥加密。本机数据密钥由 OS Keyring 保护，容器数据密钥由主密码保险库保护，禁止复用 Provider 凭据作为加密密钥。
- 加密代码变化数据在任务完成后默认保留 30 天，用户可以固定保留轨迹或提前清理。到期后仍保留脱敏意图卡、事件引用和验证摘要供只读回放，但该检查点明确标记为不可再分支；活动任务、未完成恢复和不确定副作用现场禁止自动清理。

### 8.3 记忆

- 隐私、API Key、Token、密码、私钥和凭据材料固定拒绝进入候选或长期记忆。
- 敏感拒绝只返回原因代码，不回显命中内容。
- 学习卡冲突、作用域歧义或来源失效时暂停，不交给模型自行解决。
- 删除学习卡停止未来检索，但保留历史轨迹中不含敏感正文的版本引用和审计事实。

## 9. 测试与验收

### 9.1 测试层次

- 单元测试使用 Scripted Mock、HTTP Stub、临时 Keyring/Vault 和临时目录，不访问网络。
- 集成测试覆盖 SQLite migration、事件投影、加密检查点、分支重放、恢复、学习卡版本和冲突。
- E2E 使用临时 Git 项目，跑通提问、纠正、分支验证、学习卡批准和下一任务引用。
- 真实 Provider 冒烟测试使用独立命令，默认不在 CI 运行，必须由用户显式授权并使用本机凭据。

### 9.2 强制不变量

1. 提问的工具调用数为零，文件和任务状态均不变化。
2. 创建纠正分支后，原轨迹的事件和代码状态字节级不变。
3. 新轨迹只能继承检查点之前的已确认状态。
4. Provider 不能伪造工具结果或验证通过。
5. 未批准学习卡不能进入任何后续 LLM 请求。
6. 敏感内容不能进入意图卡、事件、检查点元数据或长期记忆。
7. 每次学习卡引用都能追溯到用户批准、卡片版本和来源纠正。
8. 现有 Mock 三机制演示、`make test`、GitHub Actions 和 GitLab CI 不回退。

### 9.3 旗舰验收场景

用户提交真实项目需求，查看 Agent 意图卡，在验证失败节点提出只读问题，从该节点提交纠正并创建新轨迹。新轨迹修改代码并通过验证，用户比较两条轨迹后批准一张项目学习卡。下一个任务检索并引用该学习卡，意图卡明确展示该规则如何改变了 Agent 的决策。

该场景同时证明用户能够理解 Agent，Agent 也能够在用户控制下学习项目经验。

## 10. 实施分期与规模

四阶段必须依次交付，每阶段形成独立 Task、隔离 worktree、TDD 提交、规约审查、质量审查和新鲜验证：

1. 真实 Provider 与凭据：预计 10 万—18 万 Token、8—14 小时。
2. 意图卡与引导执行：预计 10 万—18 万 Token、8—15 小时。
3. 检查点与分支回放：预计 15 万—25 万 Token、12—20 小时。
4. 项目学习卡：预计 10 万—18 万 Token、8—15 小时。

计入规格、计划、TDD、双重评审、返工和回归，本轮总量预计约 50 万—90 万 Token、35—60 小时。估算不是额度承诺；实际消耗受模型、缓存、跨平台问题和审查返工影响。

## 11. 完成标准

本轮只有在以下条件同时满足时才算完成：

- DeepSeek 和 Qwen 均通过统一 Provider 契约；至少完成一次用户授权的真实 Provider 冒烟验收，或明确记录因用户未提供凭据而未执行，不能伪造通过。
- 引导与自动模式均可运行；结构化意图卡能够由事件重新投影。
- 用户可在语义检查点提问、纠正、创建分支和比较轨迹。
- 用户批准的项目学习卡能在下一任务被确定性检索和可追溯引用。
- 旗舰验收场景可由 Mock 完全离线、确定性重复运行。
- 所有新增安全边界均有负向测试，现有测试、演示、CI 和交付契约不回退。
