# 共学回放式工作台前端优化设计

## 1. 背景与目标

当前 WebUI 已经具备项目接入、Provider 配置、需求提交、计划审批、Agent 运行、事件流、意图卡、失败提问、纠正分支、最终审查和项目经验批准等功能，但全部内容纵向堆叠在单个 `App.tsx` 页面中。用户很难理解当前位于哪一步，原始事件的视觉权重也高于“意图—行动—结果—纠正”的共学主线。

本次把 WebUI 优化为专业教学型单页工作台，以“操作流程更清楚”为骨架，以“共学回放特色更突出”为核心。前端复用现有 API 和后端能力，不增加 Provider Probe、主动清除或其他新后端功能；完成后再以最终界面为准执行已批准的文档整理任务。

## 2. 范围与边界

### 2.1 本次完成

- 六阶段单页工作台及顶部阶段导航。
- 当前阶段自动推进、已完成阶段回看、未解锁阶段禁用。
- Mock 默认主路径和高级 Provider 设置抽屉。
- 意图优先的执行、验证、回放和纠正展示。
- 原始事件、诊断、指纹和完整技术字段折叠展示。
- 桌面答辩优先、窄屏单列可操作的响应式布局。
- 保留并增强现有可访问性、确定性安全门和凭据清理。
- 纯函数、React 和 Playwright 三层测试。

### 2.2 本次不完成

- 不修改后端 API、Agent 循环、治理、存储或部署协议。
- 不增加 WebUI Provider Probe、主动清除或真实联网验收。
- 不增加多任务、多 Agent、多级纠正分支或多条长期记忆。
- 不做专门移动端产品，也不引入 UI 组件库、图标库、状态管理库或动画库。
- 不生成依赖截图的文档；演示说明使用稳定的阶段名称和可见文本。

## 3. 信息架构与阶段模型

页面采用六阶段单页工作台：

1. 项目接入
2. 需求描述
3. 计划审批
4. 执行与验证
5. 回放与纠正
6. 交付与经验

顶部持续显示六步进度、任务状态、SSE 连接状态和全局提示。完成当前阶段后自动推进；用户可以点击已经解锁的阶段回看，尚未解锁的阶段不可进入。自动推进不能覆盖用户主动回看的选择：只有当前所查看阶段仍是流程的最新阶段时，新的证据才把视图推进到下一阶段；用户回看旧阶段时显示“返回当前阶段”入口。

### 3.1 阶段解锁规则

- `PROJECT`：始终解锁。
- `REQUIREMENT`：Workspace 已建立信任后解锁。
- `PLAN`：Task 已创建后解锁。
- `EXECUTION`：计划已批准，或任务已进入 `DECIDING`、执行、验证、等待用户/动作批准、终审或完成状态后解锁。
- `REPLAY`：出现至少一张意图卡、验证失败、危险动作阻塞、`WAITING_USER`、`WAITING_FINAL_REVIEW` 或 `COMPLETED` 时解锁。
- `DELIVERY`：最新一轮验证、diff 和最终摘要均完整，或任务已经 `COMPLETED` 时解锁。

`latestAvailableStage()` 取已解锁阶段中的最后一项；`selectedStage` 是用户当前查看项。项目切换时重置到 `PROJECT`，旧 Task、事件、卡片、比较和审批证据全部清空。

### 3.2 阻塞规则

- Workspace 未信任时不能进入需求阶段。
- SSE 重连、状态未知或操作进行中时，禁止会改变任务状态的动作，但仍可查看已收到的证据和已解锁阶段。
- 非法事件触发清空审批证据并对账；对账失败后停留在当前已解锁阶段，提示重新接入项目。
- 计划、验证、diff 或最终摘要缺失、截断、摘要不一致时，不展示相应批准按钮。
- 危险动作拦截显示原因和精确范围；当前后端没有提交该审批的 API，因此只展示确定性阻塞说明，不创建无效按钮。

## 4. 各阶段内容

### 4.1 项目接入

仅展示项目路径、接入操作、仓库摘要和建立信任按钮。Workspace 信任是本阶段完成条件。接入另一个项目前立即清除旧 Workspace/Task/事件/卡片/比较/项目经验状态以及 API Key；接入失败也不得恢复旧信任。

### 4.2 需求描述

展示编码需求、当前运行模式和最新一条经批准的项目经验。默认模式文案为“确定性 Mock 演示”；存在已配置 Provider Profile 且用户选择后显示对应 DeepSeek/Qwen Profile。提交失败时保留需求文本，方便用户修改后重试。

Provider 设置位于页头右侧“高级设置”抽屉，不构成独立阶段。抽屉说明：会话 API Key 不持久化，当前 WebUI 没有连接测试/主动清除，真实外网任务尚未验收。API Key 使用密码输入，只保存在 React state；配置成功、失败、关闭抽屉或切换项目后立即清空。抽屉支持 `Escape` 关闭、键盘焦点约束和关闭后焦点恢复。

### 4.3 计划审批

以计划正文为视觉主体，同时显示内容摘要和字节数。计划证据完整时显示“批准计划”；缺失、空白、截断或元数据不一致时显示明确阻塞说明，不提供批准入口。批准后继续复用当前行为立即触发任务运行。

### 4.4 执行与验证

默认显示当前动作/状态、最近一轮有效验证、危险动作拦截和简化事件进度。原始事件序列、完整诊断、指纹和技术字段统一放入 `TechnicalDetails` 折叠区。验证结果必须属于最新一次文件修改之后，旧轮次成功不能用于当前最终批准。

### 4.5 回放与纠正

意图卡是核心展示，每张卡显示意图、动作、预期、实际和证据状态。失败卡支持：

- 对当前失败节点提出只读问题；回答不调用工具。
- 输入纠正说明并创建唯一的单级纠正分支。

创建纠正失败时保留纠正文本。已有纠正分支后不再展示重复创建入口。父子结果在桌面使用两列比较，窄屏改为上下排列；展示父/子状态、验证摘要和 diff，不引入新的比较 API。

### 4.6 交付与经验

汇总最新一轮验证、最终 diff 和最终摘要。三项证据完整时才显示最终批准按钮；批准完成后允许用户编辑并批准一条项目经验。文案必须明确这条经验将在同一项目的下一项任务中引用，且不得包含凭据、隐私或用户未批准的信息。

## 5. 组件与状态边界

现有 `App.tsx` 拆分为以下职责清晰的单元：

- `App`：组合浏览器 API 与工作台入口，保持对现有测试注入 `HarnessApi` 的兼容。
- `HarnessWorkbench`：持有 Workspace、Task、事件、卡片、比较、项目经验和全局操作状态；协调 SSE 与阶段推进。
- `StageNavigator`：渲染六步进度、解锁/当前/完成状态、历史回看和“返回当前阶段”。
- `TaskStatusBar`：任务状态、SSE 状态和全局提示。
- `ProjectStage`、`RequirementStage`、`PlanStage`、`ExecutionStage`、`ReplayStage`、`DeliveryStage`：每个组件只接收当前阶段所需的值和回调。
- `ProviderSettings`：管理高级设置抽屉与 API Key 局部 state；密钥不进入 `HarnessWorkbench` 的可回放状态。
- `TechnicalDetails`：基于原生 `<details>` 承载技术证据。
- `EvidenceCard`、`IntentCardView`、`BranchComparisonView`：复用证据、回放与比较视觉。

阶段推导、最新有效证据选择和解锁逻辑放在无副作用的 `workflow.ts` 中。组件不重新解释 Task 状态或事件顺序，只消费这些纯函数的结果。API 类型和服务端字段保持不变。

建议文件结构：

```text
web/src/
  App.tsx
  workbench/
    HarnessWorkbench.tsx
    workflow.ts
    workflow.test.ts
    StageNavigator.tsx
    TaskStatusBar.tsx
    ProviderSettings.tsx
    TechnicalDetails.tsx
    EvidenceCard.tsx
    IntentCardView.tsx
    BranchComparisonView.tsx
    stages/
      ProjectStage.tsx
      RequirementStage.tsx
      PlanStage.tsx
      ExecutionStage.tsx
      ReplayStage.tsx
      DeliveryStage.tsx
```

## 6. 视觉与响应式规范

采用专业教学工作台风格：

- 浅灰背景、白色工作区、深蓝主色。
- 绿色表示验证成功，橙色表示等待/需注意，红色仅用于失败和治理拦截。
- 所有状态同时显示文字或图标，不只依赖颜色。
- 顶部阶段导航在桌面保持可见，当前阶段显示清晰编号、标题和说明。
- 正文适配 1280–1920px 的电脑与投影显示；最大内容宽度避免超长行。
- 小于 `760px` 时导航和所有双列布局改为单列；核心表单与按钮仍可操作。
- 代码、诊断和 diff 使用系统等宽字体与高对比背景。
- 不引入外部字体、远程图片或运行时 CDN。
- 保留语义标题、表单 label、`aria-live`、可见键盘焦点、禁用状态和合理对比度。
- 尊重 `prefers-reduced-motion`；本次不依赖动画表达状态。

## 7. 错误处理与安全

- 通用 API 错误只显示稳定提示，不呈现异常对象、响应正文或凭据。
- 需求、问题和纠正内容在失败后保留；API Key 在所有结束路径清空。
- SSE 重连时禁用 mutation，事件仍可阅读；非法事件清空审批证据。
- 切换项目销毁旧 SSE 订阅和旧任务上下文。
- 不把 Provider 的内部 `probe()` 暴露为前端能力，不添加假按钮。
- 不把真实外网 Provider、HTTPS、用户认证或 ECS 动态验收写成已完成。
- 现有 Host/Origin/session guard、摘要完整性和最新轮次验证门保持产品事实来源；CSS 或组件拆分不得绕过这些门。

## 8. 测试与验收

### 8.1 纯函数单元测试

覆盖：

- 六阶段的精确解锁条件。
- 自动推进、历史回看和返回最新阶段。
- 项目切换重置。
- 最新一轮验证/diff/最终摘要选择。
- 计划/诊断空白、截断、摘要或字节数不一致时不可批准。
- 失败、危险阻塞和终审状态对回放阶段的解锁。

### 8.2 React 组件测试

覆盖：

- 阶段导航只允许进入已解锁阶段。
- 建立信任、创建任务和批准计划后的自动推进。
- Provider 抽屉的默认 Mock 文案、键盘关闭、焦点恢复及 API Key 全路径清空。
- 技术详情默认折叠且可展开。
- SSE 重连/非法事件时 mutation 禁用与证据保留/清理。
- 失败提问、纠正说明失败保留、唯一分支和父子比较。
- 完整交付证据门和项目经验批准。

### 8.3 Playwright E2E

复用现有确定性 Mock 服务器，完成：

```text
项目接入 → 建立信任 → 需求 → 计划审批 → 执行与验证 → 回放 → 最终批准
```

E2E 断言阶段标题和关键可见状态，不依赖颜色或脆弱 CSS selector；增加窄屏视口，确认阶段导航、父子比较和表单变为单列并可操作。测试不访问真实 LLM 或公网。

### 8.4 完整门禁

最终必须通过：

```text
make test
make demo
python scripts/secret_scan.py
python -m pip check
git diff --check
```

并进行每 Task 规约符合性审查、代码质量审查和整分支最终审查。

## 9. 与文档整理任务的联合实施

已提交的文档整理计划 `docs/superpowers/plans/2026-08-14-documentation-refresh.md` 暂停执行，不废弃其批准的信息架构、归档清单和真实性边界。前端规格获批后生成一份新的联合计划，执行顺序固定为：

1. 前端阶段契约与纯函数。
2. 工作台组件拆分、Provider 抽屉与视觉样式。
3. React/Playwright 主路径与响应式验收。
4. 历史文档归档和路径修复。
5. 按最终 UI 重写 README、FEATURES、DEMO、DEPLOYMENT、SECURITY 与学生反思提纲。
6. 完整验证、双重审查、整分支审查、合并和非强制推送。

前端三个 Task 和文档两个 Task 使用同一个隔离 worktree，严格串行。每个 Task 独立 RED/GREEN、独立中文提交和独立双重审查；文档 Task 引用最终阶段名称，避免 UI 完成后再次返工。
