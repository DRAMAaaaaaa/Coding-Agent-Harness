# 可用产品优先交付策略设计

## 1. 决策状态

用户于 2026-07-16 批准采用“可验收纵向切片”方案。后续实现以尽早形成真正可使用、可演示、可验收的完整 Coding Agent Harness 为首要排序依据；非阻塞增强项可以延期，但必须形成可追踪记录。

本策略调整实现优先级和范围取舍，不降低 `SPEC.md`、课程通用要求、`AGENTS.md` 安全规则及确定性验证要求。

## 2. 最短完整产品闭环

首个完整产品必须连通以下用户路径：

1. 用户通过 WebUI 接入本地 Git 项目并输入编码需求。
2. Harness 识别项目、建立独立 worktree，并默认生成待批准计划。
3. 用户批准计划后，仓库自有 Agent 循环调用可注入的 DeepSeek、Qwen 或 Mock Provider。
4. Agent 通过受治理工具读取和修改代码；删除、越界访问、依赖安装、网络请求、Git 推送及高风险 Shell 必须等待精确审批。
5. 验证失败被确定性分类并反馈给下一轮 Provider 请求，使后续动作发生可观察变化；预算耗尽时停止并等待用户。
6. WebUI 展示状态、审批、事件、验证证据、diff 和交付文档，用户完成最终审查。
7. 离线 Mock 演示、一键测试、Docker 构建及 CI 能重复证明产品满足验收要求。

只有上述路径端到端成立，才称为“完整产品”；仅完成若干后端模块、页面外观或无法运行的接口不算完成。

## 3. 实施优先级

后续 Task 仍遵守既有依赖关系和每项 Task 的 TDD、独立 worktree、双重评审及逐 Task 提交要求，但内部工作按以下顺序取舍：

1. 先实现打通纵向闭环所需的最小稳定接口。
2. 紧接着补齐安全护栏、确定性反馈、停止逻辑和可恢复状态。
3. 尽早把接口接入 WebUI，并使用离线 Mock 跑通真实临时 Git 项目。
4. 在闭环通过后补齐容器、双 CI、部署与最终交付审计。
5. 最后处理不影响首版使用和验收的增强能力。

Task 5—10 应优先交付可供 Agent 主循环消费的必要能力；Task 9、11、12、13 构成主要产品集成阶段；Task 14 固化可重复交付。不得为了局部功能的完备度长期推迟 WebUI、E2E 或机制演示。

## 4. 不得延期的内容

以下内容属于发布门禁，不得放入延期清单：

- 课程明确要求的一键测试、GitHub Actions、GitLab `unit-test`、Docker 分发和可部署 WebUI。
- 仓库自有 Agent 循环、可注入 LLM、严格动作解析、工具分发、治理审批、反馈闭环、停止逻辑和状态持久化。
- Mock/Stub LLM 驱动且不依赖网络的确定性核心测试与三机制演示。
- 路径围栏、统一脱敏、秘密禁止持久化、一次性审批、受限 Shell、worktree 隔离和凭据不回显。
- “失败反馈进入下一轮并改变动作”这一项目主要贡献及其稳定指纹、进展预算和升级行为。
- WebUI 中创建任务、计划批准、危险动作审批、事件/验证/diff 查看及最终交付的主路径。
- 新鲜的测试、Lint、类型检查、构建、演示和交付审计证据。

## 5. 可以延期的内容

只有同时满足“不会破坏安全边界、不会阻断主路径、不是课程硬性要求、存在明确临时替代”时，功能才可以延期。典型候选包括：

- Python、Node.js 之外的额外项目类型识别。
- 不影响核心操作的界面动画、主题、复杂筛选和高级布局。
- 向量检索、跨项目智能推荐等首版不需要的记忆增强。
- 非必需工具、额外 Provider 便利功能和高级性能优化。
- 不影响正确性及验收时限的诊断体验增强。

延期不是删除需求。若实现过程中发现某项候选实际影响安全、主路径或验收，它立即恢复为当前 Task 的阻塞项。

## 6. 延期台账

实施阶段新增仓库根目录 `DEFERRED_WORK.md`，作为唯一正式延期台账。每条记录必须包含：

- 唯一编号和来源 Task。
- 未完成内容及原始验收要求。
- 延期理由和作出决定的日期。
- 对用户、测试、安全和部署的影响。
- 当前临时替代或明确说明不存在替代。
- 恢复实施的触发条件、依赖和建议优先级。
- 相关分支、提交、测试或事件证据。

不得只写模糊的“后续优化”。每个 Task 收尾时必须审查台账：新增延期项、更新已解决项，或明确记录本 Task 没有延期内容。已解决条目保留历史并标记对应提交，不直接删除。

## 7. 完成与验收规则

Task 完成仍以其被选定的发布必需范围全部通过为前提。若存在延期项，提交说明、`PLAN.md` 和 `AGENT_LOG.md` 必须一致披露，且审查者必须确认它们确实不阻断完整产品闭环。

首版产品完成需要同时满足：

- 用户主路径能够从 WebUI 走到可审查的代码与文档交付。
- 三项机制演示在离线 Mock 下确定性通过。
- 一键测试覆盖后端、前端和 E2E，重复执行结果稳定。
- Docker 与 CI 使用无真实密钥的配置成功构建和测试。
- 所有延期项均有完整台账，且其中没有发布门禁内容。

出现测试失败、安全不确定性、数据恢复歧义或验收缺口时，不得以“产品优先”为由跳过；应停止完成声明，修复阻塞问题或由用户明确缩减产品目标。

## 8. 对现有计划的影响

后续通过 `writing-plans` 更新 `PLAN.md`：修正 Task 4 已完成状态，为 Task 5—14 标注“发布必需范围”和“可延期增强”，并在每个 Task 的评审步骤加入延期台账检查。既有接口契约与依赖顺序保持不变，除非新的书面规约再次获得用户批准。
