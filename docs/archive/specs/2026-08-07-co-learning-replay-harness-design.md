# 共学回放式 Coding Harness 精简设计

## 1. 背景与目标

仓库已经具备可离线验收的 Coding Agent Harness：用户可以接入 Git 项目、输入需求、批准计划，让自研 Agent 在独立 worktree 中修改代码，并通过确定性反馈闭环完成验证、纠正和最终审查。现有实现还包含治理护栏、事件存储、REST/SSE、最小 WebUI、Mock 三机制演示、一键测试、双 CI 和 Docker 交付契约。

本扩展不重写这些能力，只增加一条具有产品特色的最小共学路径：用户能理解 Agent 在关键节点的意图，在验证失败时提问并纠正，从失败节点创建新轨迹，最后把一条经用户批准的项目经验用于下一任务。

首版成功标准是端到端故事完整、确定性、可解释和可验收，而不是提供通用回放平台或完整知识管理系统。

## 2. 精简范围

四个 CL 阶段各保留一个最小能力：

1. **CL-1 真实 Provider：** 会话 API Key、DeepSeek/Qwen 选择和现有 Agent 主路径。
2. **CL-2 意图卡：** 计划、首次修改、验证失败和最终交付四类卡片；验证失败节点支持零工具只读提问。
3. **CL-3 纠正分支：** 从一个验证失败节点创建一次纠正分支，原轨迹不变，并比较两条轨迹的最终状态、验证摘要和 diff。
4. **CL-4 项目经验：** 用户批准一条简短经验；下一任务确定性加载最近一条已批准经验并显示引用。

已实现的 Keyring 和加密 Vault 代码可以保留及继续接受安全回归测试，但不再扩展其 WebUI、管理 API 或首版验收范围。

## 3. 明确延期

以下能力不属于精简首版：

- Provider Profile 编辑/删除、持久凭据切换、Vault 解锁界面、连接 probe 和独立真实联网 smoke 命令。
- 通用语义检查点编辑器、引导/自动双模式、任意节点提问和方向变化检查点。
- 加密检查点、自动清理、任意节点恢复、多级分支、多个纠正子分支和复杂轨迹筛选。
- 学习卡复杂作用域、版本、正反示例、冲突合并、使用统计、后台管理和向量检索。
- 最终视觉设计、动画、主题、公网多用户部署、团队权限、多 Agent、依赖安装、通用工具网络和 Git push/merge/release。

延期能力不得借精简接口绕过现有治理策略，也不能在文档中描述为已经交付。

## 4. 架构

### 4.1 保留的现有边界

- `AgentOrchestrator` 仍是唯一 Agent 循环。
- `LLMProvider` 仍是 Mock、DeepSeek 和 Qwen 的共同边界。
- `TaskEvent`/`EventStore` 仍是执行事实的唯一来源。
- `ToolRegistry`、`PolicyEngine`、`FeedbackEngine`、`WorktreeManager` 和停止逻辑保持不变。
- 新增的只读提问不能获得工具 schema；Provider 联网授权不能扩展成工具联网授权。

### 4.2 IntentProjector

`IntentProjector` 是从有序任务事件到意图卡的确定性纯投影。首版不建立第二套轨迹数据库。卡片稳定 ID 由任务 ID、卡片类型和来源事件序号组成，字段固定为：

- `kind`：`plan`、`first_edit`、`verification_failure` 或 `final_delivery`；
- `intent`：面向用户的行动目的；
- `evidence_refs`：引用的事件序号与项目文件；
- `action`、`expected_result`、`actual_result`；
- `status` 与 `source_event_sequence`；
- 可选的 `learning_card_id`，表示本任务采用的项目经验。

卡片不得包含模型原始思维链、隐藏提示词、API Key、主密码或未脱敏的命令输出。

### 4.3 QuestionService

只有 `verification_failure` 卡片可以提问。服务把卡片、用户问题和有界脱敏事件摘要发送给任务已授权的同一个 Provider，但传入空工具集合。回答只解释已知事实，不执行工具、不修改任务状态、不创建 worktree。

问题和回答作为脱敏事件追加保存。Provider 失败只产生稳定错误，原任务继续停留在原状态。

### 4.4 CorrectionBranchService

验证失败时保存一个有界文本检查点：原始 Git 基准提交、规范化文本 diff、diff SHA-256 和来源事件序号。检查点位于 Harness 私有 `state_root`，不进入普通 Agent 工具能力。

用户提交纠正后，服务先把父 worktree 的写租约冻结为只读，保留其目录、分支和内容，再创建独立 worktree，从原基准恢复检查点 diff，并创建引用父任务、父事件和纠正文本的新任务。这样同一 Workspace 仍然最多一个活动 writer；原任务、原事件和原 worktree 内容不被改写。首版每个失败节点只允许一个纠正分支；重复请求返回同一分支。

### 4.5 ProjectLearningService

任务完成后可以产生一条经验候选。用户可编辑后批准；未批准候选不进入后续上下文。记录只包含项目 ID、经验文本、来源任务、来源事件和批准时间。

下一任务只加载同一项目最近一条已批准经验，把经验 ID 和文本放入 Provider 上下文，并在首张意图卡显示引用。Mock 验收必须证明该经验改变下一次动作，而不是只证明记录存在。

## 5. 最小用户路径

1. 用户在现有 WebUI 选择 DeepSeek 或 Qwen，临时输入 API Key 和编码需求。
2. API Key 提交后立即从浏览器状态清空；Harness 在创建 worktree 前验证任务具有会话凭据和精确 Provider 授权。
3. 现有 Agent 执行任务；WebUI 展示四类意图卡。
4. 验证失败卡提供“提问”和“从此纠正”。提问是零工具解释。
5. 用户纠正后创建新 worktree 和新轨迹；原轨迹保持只读。
6. WebUI 比较两条轨迹的最终状态、验证摘要和 diff。
7. 用户在最终交付卡批准一条项目经验。
8. 下一任务显示采用的经验，并由确定性 Mock 证明它改变了动作。

## 6. 最小 API 与 WebUI

主路径只需要以下能力：

- 创建和列出 Provider Profile；
- 写入会话凭据；
- 创建绑定 Provider 的任务；
- 查询任务意图卡；
- 在验证失败卡片上提问；
- 从验证失败节点创建或读取唯一纠正分支；
- 查询原任务与纠正分支的结果比较；
- 读取、编辑并批准一条经验候选。

WebUI 沿用当前单页结构，只增加 Provider 选择和密码输入、四类卡片、失败卡操作、简化分支比较、经验批准以及下一任务的经验引用提示。最终视觉设计继续延期。

## 7. 安全与错误处理

- Provider 地址由 Harness 固定登记，`trust_env=False`，不跟随重定向；用户不能提供 base URL。
- API Key 只进入会话内存，不进入浏览器存储、URL、日志、事件、异常、报告或 Git。
- 缺失或过期的 Provider 授权必须在创建 worktree 前拒绝。
- 提问始终使用空工具集合，失败不改变任务状态。
- 检查点只允许有界文本 diff；过大、摘要不匹配或 patch 恢复失败时进入 `WAITING_USER`，保留现场且不自动重试或删除。
- 原任务轨迹只追加事件，任何纠正都创建新任务。
- 含凭据、隐私信息、密钥特征或超出长度限制的经验候选整条拒绝，不保存部分内容。
- 现有治理、路径围栏、worktree 隔离、反馈预算、Mock 三机制和停止逻辑不得回退。

## 8. 测试与验收

每个精简 Task 使用红—绿—重构 TDD，只运行相关聚焦测试、Ruff、mypy 和必要的秘密扫描。任务级规约审查与质量审查合并为一个审查者；只有 Critical/Important 进入定向返工。

新增测试包括：

- Provider Profile、会话凭据、固定端点、`trust_env=False`、任务授权和 HTTP Stub 契约；
- 四类意图卡从同一事件序列稳定投影；
- 只读提问没有工具调用和任务状态变化；
- 原轨迹不变、纠正分支唯一、检查点摘要校验和 patch 失败保留现场；
- 未批准经验不进入上下文、敏感候选拒绝、最近一条已批准经验被引用并改变 Mock 动作。

只新增一个 Playwright 旗舰场景，完全使用 Mock/HTTP Stub，覆盖：验证失败 → 查看意图卡 → 只读提问 → 创建纠正分支 → 新分支通过 → 比较结果 → 批准经验 → 下一任务采用经验。

现有 CI、`make demo` 和安全负向测试继续运行。739+ 全量测试只在 CL-4 最终验收时运行一次。真实联网不是自动完成门禁；未由用户提供凭据和显式触发时必须记录“未执行”。

## 9. 精简实施单元

剩余工作压缩为五个 Task：

1. **CL-1A Provider 核心关闭：** 保留已实现的 Profile、凭据和 Registry，只关闭环境代理安全问题。
2. **CL-1B Provider 纵向接线：** 最小 API、现有 Agent runtime 和 WebUI Provider 输入一次连通。
3. **CL-2 意图卡与提问：** 投影器、失败节点提问和最小卡片界面。
4. **CL-3 单级纠正分支：** 检查点、唯一分支、恢复和简化比较。
5. **CL-4 单条经验与最终验收：** 候选、批准、下一任务引用、唯一旗舰 E2E 和中文交付文档。

每个 Task 保持隔离 worktree、单 Task 提交、聚焦 TDD、合并任务审查和新鲜验证。整条精简路线预计剩余约 10 万—20 万 Token、10—18 小时；该估算不是额度承诺。

## 10. 完成标准

只有以下条件同时满足时，精简 CL 路线才算完成：

- DeepSeek/Qwen 通过统一、固定端点、无环境代理的 Provider 契约，并能驱动现有 Agent 主路径；
- 四类意图卡可从事件确定性重建，失败节点提问零工具、零状态副作用；
- 用户可从一个验证失败节点创建唯一纠正分支，原轨迹不变，并比较最终状态、验证摘要和 diff；
- 用户批准的一条安全项目经验能在下一任务被引用，并由 Mock 证明改变动作；
- 唯一旗舰 E2E、现有三机制演示、全量测试、静态检查、秘密扫描和交付契约通过；
- 所有延期能力均如实登记，不被描述为已完成。
